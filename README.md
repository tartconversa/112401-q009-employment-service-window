# 就业服务预约积压的到期压力与窗口承接

各就业服务站使用同一服务日日历，时间用本地时刻。业务流水列受理回执、暂停及回流事实，窗口开放表来自排班。所有请求均为演练代号。

## 资料约定

CSV 使用 UTF-8，首行为列名。多值字段以竖线分隔。空单元格表示来源未填。

- policy.csv。义务时限按受理后的服务日计数。hold_days 表示站点在有效暂停开始后按规则保留已通知的预约多少服务日。segments 是完成所需连续半小时段数。 当天受理或暂停的日界，以事件时间所在服务日结束时更新状态；受理当天不计入办理义务。
  字段为 `service`、`limit_days`、`segments`、`qualification`、`can_suspend`、`hold_days`。
- calendar.csv。服务工作日用于计时。窗口另由开放表决定。
  字段为 `date`、`service_day`。
- intakes.csv。一次申请的受理日期和可办理站点。prior 是重办的来源申请，restart 以受理回执为准。
  字段为 `case`、`service`、`station`、`alternates`、`accepted`、`prior`、`restart`。
- events.csv。按时间戳发生的外部业务事实。EV 和 EG 回执可能在同一时间改变多项服务义务。
  字段为 `event`、`case`、`kind`、`at`、`site`、`receipt`。
- slots.csv。窗口连续开放时段。shared_staff 相同代表同一位可支援人员，不能在重叠时段用两次。
  字段为 `slot`、`site`、`day`、`start`、`end`、`qualification`、`shared_staff`、`status`。
- appointments.csv。已经承诺给申请人的时段。场站取消回执另在 events 中。
  字段为 `appointment`、`case`、`slot`、`start`、`end`、`notified`。
- scenarios.csv。经理可审议的积压回流假设，日期和回流下上界用于比较需求压力。
  字段为 `scenario`、`service`、`day`、`resuming_low`、`resuming_high`、`arrivals_low`、`arrivals_high`。

## 口径：两个时钟与三类责任事实

`empq/` 包把"等多久"和"会不会逾期"拆成两个独立时钟，避免旧中位数把未排到的人丢掉。

### 办理义务钟（含暂停规则，决定逾期）

- 受理当天不计；其后每个服务日按**日末状态**判断是否为活跃服务日：
  - 暂停事件所在服务日的日末已处于暂停 → 该日**不计**；
  - 回流事件所在服务日的日末已恢复 → 该日照常计 1（回流当天重新计时）；
  - 申请人未到场（`no-show`）不暂停义务钟；站点取消（`site-cancel`）也不暂停，只使原预约作废。
- 到期日 = 受理后第 `limit_days` 个活跃服务日，是日历加暂停事实的推演结果，与是否办结无关，因此可用于判断办结是否逾期。
- 重办申请 `restart=no` 且带 `prior` 时，义务钟沿用来源申请的受理锚点与暂停事实（见 C07→C05）；`restart=yes` 才另起时限，以正式回执为准。来源申请的撤回不终止已被承接的义务链。
- 日历表外的日期不做节奏假设：到期日无法推出时标注"观察窗不完整"，不判逾期。

### 等待钟（登记到预约成功，决定等待分布）

- 等待天数 = 受理日（不含）到**首次有效预约**通知日（含）之间的原始服务日数，不做暂停扣减。
- 站点取消使预约作废、申请回到未预约状态（右删失）；`no-show` 保留"曾取得明确办理时段"的事实。
- 等待分布用 Kaplan–Meier 乘积极限：取得首次有效预约为事件，观察日仍未取得者为右删失并继续留在风险集；删失过半导致中位等待不可估计时明确报出，不编造数字。旧的"近窗已办结中位数"作为对照口径并列展示，并列出它丢弃了哪些申请。

### 分桶与回流分组

- 在办申请分入：已逾期 / 今日到期 / 临近到期 / 已有有效预约 / 未预约 / 暂停等回件；已办结、已撤回单独成桶。
- 暂停件按业务×当前责任站点组成**回流队列**：义务钟冻结、不是流失，同一回件可能让整组同时回流形成瞬时压力。
- 跨站转接（`transfer`）以申请为单位保留累计服务责任，压力归入转接后的责任站点。

## 容量与互援的硬约束

`empq.capacity` 的规划顺序是先守承诺、再按逾期风险补位：

1. 观察日仍有效的未来已承诺预约全部冻结，优先占用窗口与 `shared_staff` 时间；
2. 窗口资质必须等于业务所需资质（`qualification`）；
3. `segments` 个连续半小时段必须在同一窗口内连续满足，窗口是具体时段而非可任意切分的总工时；
4. 同一 `shared_staff` 的重叠窗口互斥，确定邀请与条件容量估计共用同一套冲突账本；
5. `proposed` 互援窗口须经窗口负责人 `accept` 后才能对具体申请发约定；`defer` 只产生条件容量估计，`return` 贡献零容量；
6. 暂停期间保留的预约按 `hold_days` 推演 `hold_until`：该服务日日末是决策时点，其后仍未回流则建议还池，释放后容量才可再分配；
7. 一份申请一轮规划至多收到一条邀请，多可选地点按申请自身的站点组合匹配，不向不同团队重复承诺。

输出把**确定邀请（firm，确有时段）**与**条件容量（conditional，回流/互援假设下的估计，不是邀请）**严格分开；情景测算对回流与新受理给出低高区间和缺口区间。

## 命令行

```bash
# 任意服务日观察点：等待分布、逾期分桶、回流队列、日历不完整提示
python3 -m empq.cli observe samples --as-of 2026-11-09

# 预约建议、暂停保留处置、互援三方案比较、情景测算
python3 -m empq.cli plan samples --as-of 2026-11-09 [--accept S6] [--defer ...] [--return_ ...]

# 同一回件多案回流与当天站点取消的批次核对，规划在日末事件全部生效后重算
python3 -m empq.cli reconcile samples --day 2026-11-09

# 用后来的办结事实回检先前的压力判断，并审计已通知约定的改签原因
python3 -m empq.cli backtest samples --as-of 2026-11-06 [--eval-day 2026-11-13]

# 经办查询：单申请的到期口径、两个时钟、预约状态、暂停段与保留决策
python3 -m empq.cli case samples --case C02 --as-of 2026-11-09
```

所有命令加 `--json` 输出结构化结果，便于接入其他系统。观察点必须是已发布的服务日，否则以退出码 2 报错。

## 包结构

| 模块 | 职责 |
| --- | --- |
| `empq/calendar.py` | 服务日日历、服务日算术、日历外显式报错 |
| `empq/model.py` | 不可变领域记录与事件/状态常量 |
| `empq/load.py` | CSV 读取、表头/外键/枚举/重叠校验 |
| `empq/timeline.py` | 重办链、两个时钟、暂停段、预约视图与观察分桶 |
| `empq/metrics.py` | KM 等待分布、旧中位数对照、逾期压力、回流队列 |
| `empq/capacity.py` | 冲突账本、互援状态机、预约建议、情景测算与方案比较 |
| `empq/reconcile.py` | 同回执批次变化的合并核对与护栏 |
| `empq/backtest.py` | 事后回检、命中率口径与改签审计 |
| `empq/cli.py` | 命令行入口（中文表格 / JSON） |
